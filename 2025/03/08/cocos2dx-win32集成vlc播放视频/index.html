2. 适用范围与结论

本文使用 libVLC 3.0.21，并针对仍保留 CCSprite、CCTexture2D、sharedDirector() 等旧式 API 的 Cocos2d-x Win32 工程。较新的 Cocos2d-x 版本需要把纹理、渲染命令和 Lua 绑定部分迁移到对应接口，不能直接复制代码。

实现思路是让 libVLC 把视频解码为 RGBA 内存，随后在 Cocos2d-x 渲染阶段通过 glTexSubImage2D 更新 Sprite 纹理。这样可以复用现有场景树和 Lua 调用方式，但需要特别处理解码线程、像素缓冲生命周期和每帧纹理上传成本。

3. 前言

cocos2dx本身带有VideoPlayer组件，但是只能在Android/iOS下播放视频，并不支持win32应用。官方不提供解决方案，so，自己实现吧。

4. 关于 libVLC

一个支持大多数平台的开源多媒体核心引擎。支持win/mac/android/ios等。官方提供C++/OC(Swift)/Java(Kolin)/.NET(Mono)的绑定。

9. 验证重点与限制

  1. 示例把纹理尺寸直接设为窗口尺寸，实际项目应在拿到媒体尺寸后重新分配缓冲，避免视频比例失真和无效内存占用。
  2. libVLC 的解码回调可能运行在非渲染线程，而 draw() 会同时读取 videobuf。正式项目需要双缓冲、互斥或帧交换标记，避免上传到一半更新的像素数据。
  3. glTexSubImage2D 每帧上传整张 RGBA 纹理，分辨率较高时会产生明显的 CPU、内存带宽和 GPU 上传开销，需要用目标视频尺寸和帧率实测。
  4. 销毁时不仅要清空回调并停止播放器，还要确认没有回调继续访问已经释放的 VideoSprite 和像素缓冲。
  5. 部署时必须同时携带 libvlc.dll、libvlccore.dll 和 plugins，并检查目标程序与 libVLC 的 x86/x64 架构一致。

建议至少验证：连续播放、暂停恢复、循环播放、切换场景后销毁、重复创建销毁，以及窗口尺寸和视频分辨率不一致的情况。
